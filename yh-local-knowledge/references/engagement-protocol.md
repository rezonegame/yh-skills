# 引导型工作协议（Engagement Protocol）

本协议定义 yh-local-knowledge 启动时的"引导型接管"——技能主动引导用户，而不是等用户发指令。这是用户核心使用路径的实现：用户在一个装满杂乱资料的文件夹里启动 agent + 这个技能，技能主动接管。

核心理念：**用户只负责"丢资料"和"做几个关键决定"，其余由技能主动推进。**

## 启动即接管的标准流程

```
1. 检测环境        判断当前文件夹是否已初始化工作区
2. 初始化（若需）   建立原始资料/.knowledge/可信资产/导出结果 结构
3. 归一化格式      跑 normalize.py，把二进制资料转 markdown
4. 扫描+建索引     读归一化后的文本，更新 manifest/source-map
5. 主动简报        给用户一个"我看到了什么"的总结
6. 引导提问        问 1-2 个关键问题（不是 5 个）
7. 推荐方向        根据回答推荐 1-2 个导出包方向
8. 推进            用户确认后进入 extract → review → asset → export
```

## 第 5 步：主动简报（关键）

扫描完成后，**主动**给用户一份简报，不要等用户问。简报格式：

```text
我已经看完你这批资料了。先给你说说我看到了什么：

📊 资料概况
- 共 X 个文件：Y 个已能直接读（md/txt/csv），Z 个已转换（PDF/Word/Excel），W 个暂未提取（原因）
- 主题初判：好像是关于「XXX」的（基于高频词和文件名）
- 资料类型：学术论文 / 行业报告 / 笔记 / 网页剪藏 / 混合（具体分布）

🔍 我的初步观察（基于扫描，未经你确认）
- [1-3 条观察，如"这批资料里有 3 份互相矛盾的观点""大部分是 2023 年的""有几份明显是草稿"]

💡 我建议可以往这几个方向走（你选一个，或告诉我别的）
- A. [方向1]：适合你[目的1]
- B. [方向2]：适合你[目的2]

或者你直接告诉我：这批资料你主要想拿来做什么？
```

简报原则：
- **基于事实，不编造**。观察来自扫描到的真实内容，不是瞎猜。
- **给判断但不替用户决定**。"主题初判""初步观察"都标明是推断。
- **用具体数字和例子**，不要说"有一些资料"，要说"3 份 PDF、2 份 Word"。
- **最多 3 条观察**，不要把简报写成分析报告。

## 第 6 步：引导提问（最多 2 问）

简报后问 1-2 个关键问题，**绝对不超过 2 个**。这是和"问诊补料模式"的区别——引导型模式追求轻量。

**必问的第一个问题**（二选一式）：
> 这批资料你主要想用来做什么？
> - 学习/研究（系统理解某个主题）
> - 写作/创作（写文章、报告、内容）
> - 做产品/做 agent（提炼规格、需求）
> - 先整理成知识库（长期沉淀，以后用）
> - 其他（告诉我）

**可选的第二个问题**（只在资料明显缺失关键信息时问）：
> 我注意到[某个缺口，如"这批资料没有明确的时间范围""有几份资料似乎是残缺的"]，这个要紧吗？

不要问：你想要什么格式？要不要双链？用什么 schema？——这些是 expert 模式的事，引导型模式不该用技术问题轰炸用户。

## 第 7 步：推荐方向（根据回答分叉）

根据用户对第 6 步的回答，主动推荐方向：

| 用户目标 | 推荐导出包 | 预计产出 |
|---------|-----------|---------|
| 学习/研究 | 学习路径包 + 概念术语包 | 学习目标/阶段路径/术语表 |
| 写作/创作 | 写作素材包 | 论点/证据/案例/引用/结构建议 |
| 做产品/agent | 产品/Agent Spec 包 | spec.md/功能清单/数据模型 |
| 整理成知识库 | 概念术语包 + 互链 wiki 包 | 可浏览、可检索的 wiki |
| 不确定 | 先做概念术语包（最通用）+ 资料地图 | 基础索引 |

推荐时给出**预计产出**，让用户知道能得到什么。然后等用户确认（一句话即可），不要自己直接开跑。

## 三种用户反应的处理

**用户明确选了一个方向** → 直接进入该方向的 extract，标注为候选，走标准 review→asset 流程。

**用户说"你看着办"/"都行"/"你来定"** → 进入 fast 模式：
- 技能选一个最通用的方向（通常是概念术语包 + 资料地图）。
- 仍标注为候选，**不绕过信任闸门**——生成完还是要给用户 review。
- 明确告诉用户"我先按 X 方向出了初稿，你看完再决定要不要确认/改方向"。

**用户提出完全不同的目标** → 倾听，判断是否能用现有导出包形态满足；不能满足时，用 expert 模式自定义。

## 已初始化工作区的再启动

如果文件夹已经有 `.knowledge/state.json`（不是首次启动）：
- 不重复简报（用户已经知道有什么）。
- 改为**增量简报**：报告"自上次以来，新增/变更/删除了什么"。
- 然后问"这次想做什么"（而不是重新走完整启动流程）。

## 降级：工具不可用时

如果 markitdown 没装，normalize 阶段会有大量文件标 `fallback_metadata_only`。简报里要**如实告诉用户**：
> ⚠️ 当前环境没装 markitdown，X 个二进制文件（PDF/Word/Excel）暂时只能记录元数据，无法提取内容。运行 `python scripts/bootstrap.py --install` 可以装上，之后就能处理这些文件了。

不要假装提取了内容。这是"绝不编造"红线的具体体现。

## 不要做的事

- 不要在简报里堆砌技术术语（schema/manifest/normalization_status 等不暴露给用户）。
- 不要问超过 2 个问题（引导型模式的核心是轻量）。
- 不要在用户没确认方向前就生成一堆导出包（浪费、且绕过了"用户选择"这一步）。
- 不要把简报写成分析报告（简报是"我看到什么+我建议什么"，不是结论）。
- 不要在 fast 模式下跳过候选标记（"你看着办"不等于"我信你的提取结果"，仍要 review）。

## 与其他协议的关系

本协议是**启动阶段**的引导。一旦进入 extract/review/asset/export，仍然遵守：
- `workspace-protocol.md` 的生命周期和状态机
- `agent-contract.md` 的跨 agent 契约（特别是"候选必用户确认"）
- 现有的 review gate（信任闸门）

引导型模式不削弱任何一条现有规则，它只是让"启动"变得更主动、更对话化。
